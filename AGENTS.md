# AGENTS.md

## Purpose

This repository stores source-grounded knowledge extracted from Bitcoin educational videos.

Agents working in this repository must preserve traceability, separate historical commentary from reusable knowledge, and avoid inventing trading rules, market facts, timestamps, prices, or source claims.

## Repository Layout

- `transcripts/`: raw, timestamped source transcripts
- `knowledge/sources.md`: source registry and processing status
- `knowledge/rules.md`: reusable analytical rules
- `knowledge/glossary.md`: canonical terminology
- `knowledge/historical_examples.md`: date-specific examples and forecasts
- `knowledge/ambiguous_items.md`: unresolved transcript or visual ambiguities
- `knowledge/conflicts.md`: conflicting rules or evidence
- `knowledge/evaluations.md`: extraction and historical-application evaluations

## Local Directory Instructions

Some directories may contain a local `README.md` that defines the operational contract for files stored in that directory.

Before creating, modifying, moving, or deleting a file inside such a directory, agents must:

1. Read the directory's local `README.md`.
2. Follow its naming convention, required metadata, file format, preservation rules, and validation requirements.
3. Treat the local `README.md` as the single source of truth for directory-specific procedures.
4. Avoid duplicating those procedures in this root `AGENTS.md`.
5. Stop and report the conflict if a local instruction contradicts this root `AGENTS.md`.

Currently active local directory contracts:

- `transcripts/README.md` applies to all files under `transcripts/`.

No other directory currently has an active local contract.

## Required Reading

Before modifying any knowledge file, read:

1. `README.md`
2. `knowledge/sources.md`
3. `knowledge/rules.md`
4. The destination file being modified
5. Relevant entries in `knowledge/ambiguous_items.md`
6. Relevant entries in `knowledge/conflicts.md`
7. The corresponding transcript when a source-derived claim is involved
8. Any applicable local directory `README.md`

Do not update a rule without checking both its source record and supporting transcript.

## Core Principles

### 1. Source Grounding

Every material educational claim must be supported by:

- A valid Source ID
- A source URL or file reference
- A transcript path when transcript evidence is available
- A timestamp or section reference
- A concise evidence excerpt or faithful paraphrase

Do not present general model knowledge as knowledge extracted from a video.

Externally researched material must be explicitly labeled and kept separate from video-derived knowledge.

### 2. No Fabrication

Never invent:

- Transcript wording
- Timestamps
- Publication dates
- Price levels
- Market data
- Indicator values
- Trading results
- Analyst intent
- Confirmation conditions
- Invalidation conditions
- Confidence scores

Use `unknown`, `not provided`, or `needs review` when evidence is missing.

### 3. Separate Content Types

Always distinguish:

- `observation`: what was visible or stated
- `interpretation`: what the analyst believed it meant
- `rule`: a reusable conditional principle
- `forecast`: a claim about a future outcome
- `historical outcome`: what happened after the forecast
- `agent inference`: a conclusion generated by an AI agent

Do not convert one observation or one historical example into a general rule without adequate evidence.

### 4. Historical Levels Are Not Current Levels

Price levels, support zones, resistance zones, targets, and invalidation levels from old videos belong in `knowledge/historical_examples.md`.

They must not be added to `knowledge/rules.md` as permanent values or reused as current levels without fresh market data.

### 5. Transcript Invariants

These repository-wide invariants always apply:

- Never invent transcript text, timestamps, source metadata, or speaker intent.
- Never rewrite raw evidence to make an extracted rule appear better supported.
- Preserve traceability between the Source ID, transcript file, timestamp, and extracted knowledge.
- Record unresolved wording, visual dependencies, and uncertain corrections in `knowledge/ambiguous_items.md`.
- Do not store content when doing so would violate applicable access or copyright restrictions.

All transcript-specific naming, formatting, metadata, maintenance, and validation procedures are defined exclusively in `transcripts/README.md`.

### 6. Visual Dependencies

When a claim depends on a chart, indicator layout, color, arrow, drawn level, or on-screen value, set:

```text
requires_visual_review: true
```

A transcript-only review cannot mark such a rule as fully verified.

### 7. Probabilistic Language

Preserve the strength of the source claim.

Examples:

- `may` must not become `will`
- `more likely` must not become `confirmed`
- `I think` must not become an objective fact
- A source author's numeric probability must remain attributed to that source and historical context

Do not create new probability percentages without a documented statistical method.

## Rule Status Policy

Allowed statuses:

- `candidate`
- `needs_visual_review`
- `verified`
- `conflicted`
- `deprecated`
- `rejected`

Agents may create `candidate` rules.

Agents must not upgrade a rule to `verified` unless the supporting source, transcript, timestamp, and any required visual evidence have been reviewed and are sufficient.

When evidence conflicts, set the rule status to `conflicted` and add an entry to `knowledge/conflicts.md`.

Do not delete deprecated or rejected rules. Preserve their history and document the reason for the status change.

## Source Requirements

Before adding knowledge from a new source:

1. Add a source record to `knowledge/sources.md`.
2. Assign a unique Source ID.
3. Follow the relevant local directory contract when creating or modifying source evidence.
4. Confirm that all recorded paths resolve to the correct files.

Use the canonical source-record template defined in `knowledge/sources.md` rather than duplicating it here.

Do not claim a publication date when only the processing date is known.

## Conflict Handling

Never silently choose one conflicting rule over another.

For each conflict, document:

- Conflict ID
- Related Rule IDs
- Related Source IDs
- Nature of the conflict
- Evidence supporting each side
- Possible reason for the difference
- Current resolution status

Possible explanations such as market regime, timeframe, or methodology differences must be labeled as inference unless directly stated in a source.

## Analysis Restrictions

When using this repository for current Bitcoin analysis:

- Verify that current data is recent and timestamped
- Cite the Rule IDs used
- Separate current observations from retrieved rules
- State missing evidence
- Include invalidation conditions
- Allow `no trade` or `insufficient data` as valid conclusions
- Do not present outputs as guaranteed financial advice

Do not place, modify, or cancel real exchange orders.

Do not request or store exchange API secrets in this repository.

## Evaluation Requirements

Evaluation must prevent future-data leakage.

For historical tests:

- Use only information available at the analysis timestamp
- Record the analysis timestamp
- Record the evaluation horizon
- Keep later outcomes separate from model input
- Include fees, slippage, and funding in trade-like evaluations
- Record both successful and unsuccessful examples
- Prefer out-of-sample and walk-forward evaluation

Do not select only favorable examples.

## Editing Rules

- Preserve existing IDs.
- Do not reuse deprecated, rejected, or removed IDs.
- Prefer small, reviewable changes.
- Avoid reformatting unrelated content.
- Do not overwrite user-authored notes without explicit instruction.
- Maintain valid relative Markdown links.
- Use UTF-8 encoding.
- Keep terminology consistent with `knowledge/glossary.md`.
- Do not add secrets, credentials, private keys, seed phrases, or personal data.

## Validation Checklist

Before completing a change, verify:

- All referenced files exist.
- Applicable local directory instructions were read and followed.
- Every new rule has a unique Rule ID.
- Every new rule has a Source ID, evidence path, and timestamp where available.
- Historical values were not added as permanent rules.
- Ambiguous transcript terms were recorded.
- Visual dependencies were marked.
- Conflicts were not silently removed.
- Markdown headings and code fences are valid.
- Relative links resolve correctly.
- No secrets or credentials were added.
- No real trading action was enabled.

## Rollback

Knowledge changes should be made in a dedicated commit or pull request.

If a change introduces unsupported rules, broken references, incorrect attribution, modified raw evidence, or leaked future information, revert the relevant commit rather than hiding the original modification.
